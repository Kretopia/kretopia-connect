# P0 fixes, 2026-11-13: what changed, how to verify, how to apply

Status: internal working document. **Nothing here is applied to production or deployed.** It records five fixes made in code, the checks to run on production first, and the order to apply them. It complements the reviews in this folder; it does not replace them, and it does not claim compliance, certification or production readiness.

How the fixes map to the reviews: wallets → **SEC-01** (P0-1 in `mentor-feedback-remediation-plan.md`); Desk agent → **AI-02**, part of **AI-03** and **SEC-09** (P0-3); invoices → **PAY-01** context and the provider-reference migration already in the repository. Two are findings the reviews do not list: the receiver of a direct message could rewrite it, and the Stripe event ledger processed an event when its own write failed.

## Before anything: read production

Run `docs/security/VERIFY_P0_FIXES_20261113.sql` in the SQL editor of the production (legacy) database. It is one read-only query that never raises. Before applying: the four migration lines read **NOT APPLIED** and no line reads **PROBLEM**. A PROBLEM line names what to fix first. It was run on a local PostgreSQL 16 with Supabase-shaped roles on an empty database (no error) and on a production-shaped one, before and after the migrations.

## Wallets

- **Gap:** the INSERT policy on `wallets` checks only `user_id = auth.uid()`. A member with no wallet row could create one with any balance and any credits (UPDATE and DELETE were already closed in 20260823223419).
- **Fix:** `supabase/migrations/20261113100000_wallets_client_insert_starts_empty.sql`. For a row inserted by `anon` or `authenticated`, a trigger sets balance 0, credits at most the 10 welcome credits (the signup grant), currency USD and the timestamps. Nothing is refused, so `WalletCard`'s fallback insert (`credits: 10`) keeps working. It checks `current_user`, so the service role, the SQL editor and SECURITY DEFINER functions (`create_wallet_for_user`, `wallet_credit`) are unaffected. No existing row changes.
- **Tested:** on PostgreSQL 16: forged balance, credits, currency and date are replaced; another member's `user_id` is still refused by RLS; SECURITY DEFINER and service-role inserts keep their values; the file applies twice. `src/lib/__tests__/security/walletAndMessageGuards.test.ts`.
- **Rollback:** in the file header.
- **Not covered:** client-written `transactions` rows (**SEC-02**): needs a decision on which flows still write them from the browser.

## Messages

- **Gap:** the UPDATE policy on `messages` is `USING (auth.uid() = receiver_id)` with no column limit. The receiver could rewrite the text, attachments or reply quote of a message someone else sent, or re-point `sender_id` at a third person.
- **Fix:** `supabase/migrations/20261113101000_messages_receiver_updates_read_state_only.sql`. The API roles keep UPDATE on the `read` column only, and a trigger refuses any other change for them even if grants drift (it compares whole rows, so columns only production has are covered). The app only ever sends `{ read: true }` (checked by the test); voice-note transcripts are written with the service role.
- **Tested:** on PostgreSQL 16: before, the receiver rewrites text and sender; after, marking read or unread works, every other change is refused, the sender still cannot update, service-role and SECURITY DEFINER writes work, and with the table grant restored the trigger still refuses. Same test file.
- **Rollback:** in the file header.

## Desk agent

- **Gap (AI-02):** `desk-agent` posted an AI-written message into project chat (`send_message_to_collaborator`) and opened a call room whose join link goes to every member (`start_video_call`) as soon as a model chose to. Approved message actions posted the text `undefined` (the direct-call path dropped the message). Executed tools left no per-action record.
- **Fix:**
  - `supabase/functions/_shared/deskApproval.ts` (new, pure): those two tools run only on a call from a door that ran them after approval: the orchestrator executing an approved action (desk-agent proves the approval record with `executionGuard`, for this tool and this project) or the copilot executor running an approved plan. Anything else, including desk-agent's own model, queues an `orch_actions` proposal with a preview, the same flow and approval card as `remove_collaborator`.
  - `supabase/functions/desk-agent/index.ts`: applies the gate; posts the approved text; tells the model these tools wait for approval; writes one `orch_actions` row per tool it ran on its own authority (`auto_executed`, `executed` or `failed`, with result or error) under the turn's run. Tasks, reminders, drafts and Credits stay immediate, now recorded.
  - `supabase/functions/agent-orchestrator/index.ts`: the automatic tier strips `_`-prefixed fields from model arguments, so a model cannot write an approval marker into a call.
  - `supabase/functions/_shared/approvalHardening.ts`: an approval may edit a message's text, not the project it goes to.
  - `supabase/migrations/20261113102000_start_video_call_requires_approval.sql`: one registry row, so the orchestrator proposes the call instead of running it.
- **Tested:** `src/lib/__tests__/edge/deskAgentApproval.test.ts` runs the real handler on an in-memory database: queued message and call, immediate and recorded task, model-written markers ignored, unmarked direct call queued, approved action runs once proven and is refused without an approval record or for another project, approved plan runs and is recorded. 9 of its 13 tests fail on the previous code. Existing agent and edge suites pass (39 files, 702 tests).
- **What users see:** asking Kreto in Desk to message someone or start a call shows an approval card; nothing is posted until they approve.
- **Not covered:** `draft_invoice` and `draft_quote` still run immediately on the Desk path (they create drafts and send nothing); they are `requires_approval` in the registry, so they appear in the weekly review query of `ai-agent-governance-review.md` and need a decision. AI-01, AI-04 to AI-06 and the other agent doors are unchanged.

## Payments

- **Gap:** a payment the issuer recorded (`confirm_invoice_paid_manually`) looked the same to others as one Stripe confirmed. Production has no `invoices.stripe_payment_intent_id`, so the marketplace webhook's paid update, which names that column, fails: every paid invoice in production today is issuer-recorded.
- **Fix:** apply the reviewed `supabase/migrations/20261015100000_invoices_provider_reference.sql` (column, client write revoke, no client insert of a paid invoice). It needs 20260904180000 (column-level UPDATE grants on invoices): line 13 of the verification query checks it. In the app, `paidProvenanceNote` (`src/lib/invoiceProvenance.ts`) labels a paid invoice without a provider reference "recorded by the issuer" for others and "self-reported" for the issuer, in the invoice list, the project finance hub and the Studio money section. Those screens select `*`, so they work before and after the migration.
- **Tested:** the migration on PostgreSQL 16 (a client draft is accepted; a paid insert or a made-up reference is refused; the service role writes the reference); `src/lib/__tests__/invoiceProvenance.test.ts`.
- **Not covered:** refunds and disputes (**PAY-02**, **SEC-19**), reconciliation (**PAY-04**).

## Stripe event ledger

- **Gap:** when the ledger insert failed for any reason other than a duplicate, the webhooks processed the event anyway, so two overlapping deliveries could both act on it.
- **Fix:** `supabase/functions/_shared/webhookLedger.ts` now tells two failures apart. A ledger that is itself broken (PostgreSQL classes 22, 23, 42; PostgREST `PGRST2xx`) fails every delivery the same way, so the event is still processed and the webhook logs `STRIPE EVENT LEDGER CANNOT BE WRITTEN`: refusing would stop every payment. Any other failure (timeout, connection, no code) answers 500 before processing anything, so Stripe delivers the event again. `guest-wallet-webhook` now uses the shared claim like the other two.
- **Tested:** `src/lib/__tests__/webhookLedger.test.ts`, `src/lib/__tests__/edge/marketplaceWebhookScenarios.test.ts` (the real handler: 500 and nothing written while the ledger is unavailable, then exactly one payment on the retry; a broken ledger still records the payment), `src/lib/__tests__/security/stripeWebhookControls.test.ts`.
- **To watch after deploy:** lines 18 to 22 of the verification query, and the webhook logs for either message.
