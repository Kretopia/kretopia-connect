### The most material finding

Edge Functions import **11 distinct version specifiers of `@supabase/supabase-js`** across the codebase, ten pinned and one floating `@2` tag:

```
 79 × https://esm.sh/@supabase/supabase-js@2.57.2
 52 × https://esm.sh/@supabase/supabase-js@2          ← floating major
 47 × @2.49.4   39 × @2.45.0   10 × @2.39.3
  3 × @2.45.4    3 × @2.38.4    1 × @2.7.1  (etc.)
```

plus two `deno.land/std` versions (114 × `0.190.0`, 108 × `0.168.0`). Each `esm.sh` import is fetched at deploy/run time with no integrity hash and no lockfile. **A remote registry compromise or an upstream tag move silently changes deployed code**, and no SBOM can currently describe what actually ran.

## 2. SBOM plan

### 2.1 Package managers and lockfiles

| Step | Action | Output | Status |
|---|---|---|---|
| S1 | Choose **one** package manager for the web build (npm, matching CI) and delete or archive the other lockfiles | One lockfile in the repo | Proposed |
| S2 | Commit to `npm ci` in CI (not `npm install`) so the lockfile is authoritative | CI uses `npm ci` | Proposed |
| S3 | Add `"packageManager"` and `"engines"` to `package.json` | Reproducible runtime | Proposed |
| S4 | Replace `bun.lockb` (binary) with nothing, or a text lock if bun is kept | Reviewable lock | Proposed |
| S5 | Add a Deno lockfile and import map for Edge Functions; replace `@2` with exact versions | `deno.lock` + `deno.json` | Proposed |

**Note:** `esm.sh` / `deno.land` URL imports must be migrated to an import map before a meaningful lockfile exists. Until then, the Edge SBOM must be generated by parsing source URLs and is inherently approximate.

### 2.2 Dependency inventory

| Step | Action | Tooling (no install required for planning) |
|---|---|---|
| S6 | Generate a CycloneDX SBOM for the web app | `npm sbom --sbom-format cyclonedx` (npm ≥ 10) or `cyclonedx-npm` |
| S7 | Generate a **separate** SBOM for Edge Functions from the import graph | Script that parses `supabase/functions/**` imports; record resolved version per function |
| S8 | Record native wrapper dependencies (Capacitor plugins, iOS pods, Android Gradle) | Capacitor CLI / Gradle / CocoaPods SBOM steps |
| S9 | Record build toolchain versions (Node, npm, Vite, TypeScript) | `package.json` + SBOM metadata |
| S10 | Attach the SBOM to each release as a build artifact and keep the last N | CI artifact store |
| S11 | Include licence and supplier fields so the SBOM can answer "what OSS is in the product" | CycloneDX `licenses`, `supplier` |

**Minimum viable SBOM:** components with name, version, purl, licence, and the deployment target (web / edge / native). Recommended format: **CycloneDX JSON** (widely supported, diffable).

### 2.4 Vulnerability scanning

| Step | Action | Cadence |
|---|---|---|
| S17 | Enable Dependabot (or equivalent) for npm, GitHub Actions and Gradle/CocoaPods | Continuous |
| S18 | `npm audit --production` (or `osv-scanner`) in CI, non-blocking on low, blocking on high/critical with a documented exception file | Every PR |
| S19 | Scan the Edge import graph against OSV for the pinned URL versions | Weekly + on deploy |
| S20 | Secret scanning on push (provider-native or `gitleaks`) | Every push |

**Honest limitation:** scanning the source does not prove the deployed bundle is clean. Step S10 (SBOM per release) is what closes that gap.

|---|---|---|

### 2.6 Release verification

| Step | Action | Acceptance |
|---|---|---|
| S24 | Build from a clean checkout with `npm ci`; fail if the lockfile changed | CI fails on lockfile drift |
| S25 | Emit a build manifest: commit SHA, SBOM digest, artifact hash | Manifest stored with the release |
| S26 | Populate `version.json` at build time with the commit SHA, not `"dev"` | `GET /version.json` returns the deployed SHA |
| S27 | Verify the deployed function set matches the intended list and JWT flags | Post-deploy check fails on drift |
| S28 | Sign or attest the release artifact (SLSA-style provenance or a signed checksum) | Verifier can confirm origin |
| S29 | Keep the previous artifact and SBOM for rollback | Rollback restores both code and SBOM |
| S30 | Record which SBOM corresponds to which production date | Audit answerable |

### 2.7 Container configuration (mentor question)

**Finding:** there is **no container definition** in this repository. The web app is a static bundle on managed hosting; the API is managed Deno Edge Functions; mobile is a Capacitor wrapper. The mentor's "container configuration" concern therefore maps to three things that *do* exist:

1. **Edge runtime configuration** — per-function JWT flags and secrets (see `security-review.md` SEC-05/SEC-23).
2. **Static hosting configuration** — CSP is currently minimal (`index.html:5`: `object-src 'none'; base-uri 'self'; upgrade-insecure-requests`), with no `frame-ancestors`, `script-src` or `connect-src` policy, and no `_headers`/`_redirects` file in `public/`.
3. **Mobile wrapper configuration** — remote `server.url` and `cleartext: true` (`capacitor.config.ts:7-9`), which is a transport-configuration issue equivalent to a weak container baseline.

**Proposal:** treat these as the "container baseline" for this architecture: documented, versioned, and verified after each deploy. If a container is introduced later (e.g. self-hosted functions), add a minimal base image, non-root user, read-only filesystem, pinned digest, and image scanning before first deploy.
