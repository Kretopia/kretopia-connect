# Security baseline

Facts below are from the repo and read-only catalog queries on production, 2026-10-19. Secret **values** are never recorded. Severity: **P0** fix now, **P1** this sprint, **P2** backlog.

## 1. RLS and grants
- **P0, closed 2026-10-19: project takeover.** `projects` UPDATE policy "Users can update accessible projects" is `created_by = auth.uid() OR user_has_project_access(...)` with no `WITH CHECK`, and `authenticated` can UPDATE `created_by`, so any accepted collaborator (guest and client roles included) could make themselves owner. Migration M0a (`docs/roadmap/schema-impact-report.md`, file `supabase/migrations/20261019120000_guard_project_created_by.sql`) was approved and applied: trigger `trg_guard_project_created_by` rejects a changed `created_by` for any signed-in caller. Verified: a member's takeover attempt raised `projects.created_by is immutable`, owner unchanged. The policy itself still has no `WITH CHECK` (other columns remain member-editable); tighten in M1. Closed since the October report: self-accept role pin (trigger `trg_guard_project_collaborator_self_update`), `match_copilot_memories` (no `anon` or `authenticated` EXECUTE).
- ~~**P1, new 2026-10-20: payer authority on `projects` is writable by any accepted collaborator.**~~ **Fixed 2026-10-20 (M6 applied, migration `20261020130000`): only the owner or the service role can change them.** Original finding: `client_user_id`, `agent_user_id`, `creative_user_ids` and `agent_mode` are updatable by guests and members, and the milestone and escrow paths trust `client_user_id`. Verified read-only (one rolled-back write test); no sign of use (0 of 75 projects have a client set, 0 paid milestones). Report: `schema-impact-report.md` M6.
- 0 public tables without RLS. 11 `INSERT ... WITH CHECK (true)` intake policies (`analytics_events`, `client_error_logs`, `event_analytics_events`, `event_share_clicks`, `site_analytics`, `newsletter_subscribers`, `email_unsubscribes`, `guest_rsvps`, `circle_guest_rsvps`, `partner_signups`, `partner_submissions`). Intended, but unbounded: add rate limiting or a size cap. **P2**
- ~~**`call_transcripts` UPDATE**~~ **fixed 2026-10-20 (M5 applied, migration `20261020120000`): no client UPDATE remains.** Original finding (policy "creator can update own transcript", `created_by = auth.uid()`): the `authenticated` role holds UPDATE on **every column**, including `recording_id`, `created_by`, `project_id`, `call_kind`, `call_id`, `participants`. Consequences: a creator can point their row at another project (injecting an entry into that team's Recordings) or at another recording id, and `get-recording-link` then mints a Daily link for it (it authorises on `created_by`, then trusts `recording_id`). Needs a victim's recording UUID, so not trivially exploitable. **P1**. Fix, not applied: remove client UPDATE entirely (verified 2026-10-20: only the service role writes this table, the frontend never updates it). The written schema-impact report is `schema-impact-report.md` M5; it needs explicit approval; no SQL is included on purpose.
- 183 SECURITY DEFINER functions are executable by `anon`. The 25 sensitive ones sampled check `auth.uid()` or an admin role and pin `search_path`; six no-argument ones are trigger functions. Known oracle: `is_meeting_member(meeting, user)` answers membership to anonymous callers. Revoke `anon` on non-public RPCs. **P2** **Triaged 2026-10-20 in `ANON_EXECUTE_TRIAGE.md`: do not blanket-revoke** (PUBLIC holds EXECUTE, and about a hundred RLS policies open to the public role call the membership predicates, so a revoke would turn empty results into errors on anonymous pages). Two items worth a fix later: the invite-token mint and the predicate oracle.
- Transcript visibility for meeting, event, and stage calls is host-only by design (migration `20260915100000`). Do not widen without a product decision.

## 2. Storage
- 11 public buckets since 2026-10-20 (`feedback-screenshots` was made private, M9; originally 12: avatars, campaign-media, email-assets, event-photos, feedback-screenshots, listing-images, location-images, location-photos, media, opportunities, partner-logos, portfolio). `feedback-screenshots` could have held personal data; it is now private (M9, closed).
- **Decision 2026-10-20 (taken on the owner's delegation): keep both `database_export_*` buckets for now, do not delete.** Deleting is irreversible, they are unreadable by any client, and the platform's own restore path (plan, backups, PITR) has not been confirmed in the dashboard, so these may be the only restorable copies of those dates. They cost about 158 MB of storage, which is not part of the database size. Delete them, after copying offline if wanted, once backups and PITR are confirmed and one restore has been rehearsed (`BACKUP_RECOVERY.md`). Inspected 2026-10-20 (metadata only, contents not opened): `database_export_13_07_26` (1 object, 62 MB, created 2026-07-13) and `database_export_28_09_26` (1 object, 96 MB, created 2026-09-28); no size limit, no MIME restriction. None of the 66 `storage.objects` policies mentions them or matches them by negation, so no client role can read them; only the service role and the dashboard can. Nothing in the repo references them. They are most likely full dumps (personal data) kept in the same project as the data they copy, with no retention. Deleting is irreversible, so it is left for the owner: confirm what they are, copy offline if still needed, then delete. **P1** (exposure low, blast radius high if the service key leaks)
- Private: `meeting-recordings`, `payment-proofs`, `dispute-evidence`, `project-files`, `message-attachments`, `deal-memos`, `product-files`, `import-uploads`, `board-assets`, `outreach-media`. Recording playback goes through `get-recording-link` (Daily access link, `valid_for_secs=3600`); the last link is also cached in `call_transcripts.recording_url` and is readable by anyone who can SELECT the row. Authorised viewers only, but treat it as a bearer URL. **P2**
- Daily recordings live in Daily's storage, retention placeholder 90 days (`_shared/recordingRetention.ts`), no purge deployed (needs migration `20260915110000` first).

## 4. Edge Function authorisation and input
- JWT verification is configured per function in the dashboard; `supabase/config.toml` lists one. A CLI deploy resets it: always set it explicitly (`DEPLOYMENT_RUNBOOK.md`). **P1**
- **Closed (fix in the SSRF PR after #227): unauthenticated URL fetchers.** `fetch-og-data` and `fetch-portfolio-data` fetched user-supplied URLs behind a hostname-substring blocklist (`169.254.170.2`, `[::1]`, `[::ffff:127.0.0.1]`, redirects, or names resolving to internal addresses all got through; `fetch-portfolio-data` chose its branch with `url.includes("spotify.com")`). Both now go through `_shared/ssrf.ts` `safeFetch` (every redirect hop re-validated). The shared guard itself had a bypass: IPv4 inside IPv6 hex form (`[::ffff:7f00:1]`, which is how the URL parser writes `[::ffff:127.0.0.1]`) was not blocked; fixed. `fetch-youtube-playlist` only reaches `www.youtube.com`; its `playlistId` is now validated. `fetch-og-data` also marked `imdb.com.evil.example` as a verified domain (substring match); now exact or subdomain. Remaining: DNS rebinding between check and fetch, and no response-size cap. **P2**
- 21 public service-role functions (OG images, sitemap, payment-link and invoice info, unsubscribe, `lookup-auth-providers`, `validate-event-promo`, `production-detail`, `redeem-project-share`): confirm each returns only what its token or public link entitles. `lookup-auth-providers` can enumerate accounts. **P1**
- AI endpoints without a session were closed here (`generate-match-explanation`, `generate-ice-breakers`); 27 functions have rate limiting, the rest do not. **P2**
- 500 responses across most functions echo `error.message`. Rule in `RELIABILITY_RULES.md`; fix per function when touched. **P2**
- CORS is `*` on all functions; acceptable with bearer auth, not for cookie auth.
- ~~Sentry Replay records text and media unmasked~~ fixed: `src/lib/sentryInit.ts` masks all text and inputs, blocks media, captures no network bodies. Production has no DSN today, so nothing was being recorded (`SENTRY_PLAN.md`).

## 5. Secrets at risk (names only)
`SUPABASE_SERVICE_ROLE_KEY` (used by nearly every function; one leak bypasses all RLS), `CRON_SECRET` (rotated 2026-10-06 after a leak), `DAILY_API_KEY` (account-wide: every room and recording), `DAILY_WEBHOOK_HMAC_SECRET`, `STRIPE_SECRET_KEY_*` and Stripe webhook secrets, `LOVABLE_API_KEY` (AI spend), `TELEGRAM_API_KEY`, `SUPABASE_ACCESS_TOKEN` (deploy), `SENTRY_AUTH_TOKEN`. Rotate on any exposure; never paste values into chat, issues, or logs.
