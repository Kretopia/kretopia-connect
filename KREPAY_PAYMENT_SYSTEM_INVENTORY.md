# KrePay Payment System Inventory

Read-only. No code, database, or provider state was changed to produce this report. No charges, transfers, payouts, refunds, invoices, connected accounts, or payment links were created.

## Method note

This inventory groups Kretopia's 32 payment-related edge functions, 23 payment-related tables, and 10 payment-related RPCs by capability cluster rather than one row per file — with that many surfaces, a flat one-row-per-function table would be less accurate, not more, given evidence depth genuinely varies per function. Every function/table named below was confirmed to exist via direct source read or the generated `src/integrations/supabase/types.ts` (which reflects the live schema, not migration history guesswork). Functions marked **[read in full or in depth]** had their actual logic inspected; functions marked **[named, not read this pass]** are confirmed to exist (via `ls supabase/functions` and cross-referenced call sites) but their internals were not inspected in this pass — do not treat their behavior as verified beyond what's stated.

## Summary of what this inventory changes about the task's starting assumptions

1. **A "manual/offline payment" mechanism already exists, twice, and was recently security-hardened** (`confirm_invoice_paid_manually` on 2026-08-12, `confirm_milestone_paid_offline` on the same date, with a further RLS pass on 2026-08-25 — the single most recent migration in the entire repository). Any "Manual SEPA Invoice Flow" work should extend and add SEPA-specific instructions/UI to these, not design new authorization plumbing from zero.
2. **The wallet balance model is already fully server-authoritative** (`wallet_credit`/`wallet_debit` are `service_role`-only). The "no client-writable balance" requirement is not a future goal — it's already true.
3. **`wallet-add-bank` is already SEPA-country-aware** (IBAN validation for DE/FR/NL/ES) at the validation layer, even though the transport is still Stripe Connect.
4. **PowerTranz does not exist in this codebase.** Treat any Caribbean-rail plan as starting from zero.
5. **Refund handling has a real, confirmed gap**: no generic refund edge function was found. This needs to be resolved (how do refunds actually happen today?) before any provider-parity claim can be made honestly.
6. **The guest wallet system was not surveyed in depth this pass** and should not be assumed to share the main wallet's already-verified security properties until it is.
