### Screen-reader proxy (accessibility tree)

Read the full accessibility tree for the Hire Talent form: every field has a real, correctly paired `label`+`textbox`/`combobox` role and accessible name (Company Name *, Work Email *, Logo, Title *, Type, Location Type, Compensation, Description *, Requirements, Deliverables, Add skills), comboboxes expose real `option` elements with correct `selected` state, and the `SectionHeading` components built in the prior report render with correct heading roles. **Not a real screen reader** (no VoiceOver/NVDA/JAWS available in this environment) — the accessibility tree is the best available proxy for what one would announce, documented as such rather than overclaimed.

### Slow-network checks

**Not achievable with this session's tooling.** No network-throttling control is exposed by the available browser tools (checked `preview_logs`, `read_network_requests` — neither exposes throttling). Documented as a real, unmet gap rather than skipped silently.

### `prefers-reduced-motion: reduce` — live emulation

**Not achievable with this session's tooling**, confirmed again this pass (same conclusion as the prior report): `resize_window` only exposes `colorScheme` (light/dark), not a motion-preference override, and there is no way to inject a `matchMedia` override before a fresh page's React tree mounts (any override made via `javascript_exec` runs in the *current*, already-mounted page — a subsequent `navigate` call loads an entirely fresh JS context that discards it). Genuine tooling limitation, not an oversight.

### Invisible-content-when-motion-reduced — static analysis sweep

Given live emulation isn't possible, ran a systematic static sweep instead — arguably more thorough than sampling a handful of pages live, since it covers every file, not just the ones visited:

- Searched all `.tsx` files for a zero-opacity `initial` animation state (`initial={{ opacity: 0, ... }}`): **15 files**.
- Cross-checked how many of those also gate on `useReducedMotion()`: **only 1**.
- Manually inspected the pattern in each of the other 14 to judge real risk, not just count matches. Most (`ThrivePromptHero.tsx`, `OneWedgeLanding.tsx`, and others) use plain `initial`/`animate` (not `whileInView`) — these always resolve to their visible end-state immediately on mount, regardless of motion preference; the real gap there is that they still *animate* under reduced motion (a Section 8 token-compliance gap), not that content stays invisible.
- **A genuine, real finding**: 3 of the 15 (`ProductReelSection.tsx`, `CreatorDashboardSection.tsx`, `ThriveFundShowcase.tsx`) plus 4 more found by the same sweep (`SpotlightFeedRow.tsx`, `ProfileHubCard.tsx`, `MorningPulse.tsx`, `EventsNearYouSection.tsx`) use `whileInView` — a scroll-triggered reveal — with no reduced-motion gate. Traced where these actually mount: **`CreatorDashboardSection.tsx` is dead code, never imported anywhere**; but the other 6 are real, live components mounted on `UnifiedHome.tsx` — **the authenticated Today dashboard, the single highest-traffic page in the product.** Under reduced motion, these still wait for scroll-triggered reveal rather than showing content immediately; in the narrow edge case where the `IntersectionObserver` never fires for a given user's navigation pattern, content could remain at zero opacity indefinitely.
- **Not fixed this pass** — 6 separate files each need individual, careful review to add the guard correctly, and this is exactly the kind of finding that deserves its own careful pass rather than a rushed fix bundled into an already-large combined task. Listed explicitly here as release-relevant, not silently deferred.
