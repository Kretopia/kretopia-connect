# Studio Container Alignment Report

Read-only source comparison. No feature files were edited to produce this report.

## Canonical Studio reference (verified from source)

Source: `src/pages/WorkHome.tsx` — both `CreatorWorkHome` (line 549) and `BrandWorkHome` (line 217), the two real render paths behind `/desk`.

```
Header:   FeaturePageHeader — full-bleed, sits above the body container entirely
Body:     <div className="max-w-6xl mx-auto px-4 pt-4 pb-36 md:pb-12 space-y-5">   (Creator)
          <div className="max-w-6xl mx-auto px-4 pt-4 pb-24 md:pb-12 space-y-5">   (Brand)
```

- Max width: `max-w-6xl` (1152px), flat at every breakpoint — no `container` utility involved.
- Horizontal padding: `px-4` (16px), flat at every breakpoint — no `sm:`/`md:` escalation.
- Top padding: `pt-4`.
- Bottom padding: asymmetric — `pb-36`/`pb-24` on mobile (bottom-nav clearance), collapsing to `pb-12` at `md:`.
- Vertical rhythm between sections: `space-y-5`.
- Tailwind's own `container` utility (`theme.container` in `tailwind.config.ts`) is a **different, unrelated construct** — `center: true, padding: "2rem"`, unbounded width until `2xl: 1400px`. Studio's real body container never uses it. Any surface using `container` is not using Studio's canonical shape, regardless of what `max-w-*` is layered on top of it, because `container`'s own 2rem (32px) padding stacks with whatever explicit `px-*` is also applied.

## Summary

Zero of the seven surfaces currently match Studio's canonical container exactly. Every surface either (a) stacks Tailwind's `container` utility with an explicit `max-w-*` — a real, structural double-padding bug, not just a style preference, since `container`'s own 2rem padding adds to whatever `px-*` is also declared — or (b) uses a `max-w-*` narrower than `max-w-6xl` (ranging from `max-w-2xl` at 672px up to `max-w-5xl` at 1024px, against Studio's 1152px), or both. Two surfaces (Match, Founding Circle) have a second redundant `mx-auto` wrapper rather than one clean container. Founding Circle additionally renders a container *before* the header, which needs a source read to classify correctly rather than assumed. No surface currently reproduces Studio's asymmetric mobile-bottom-nav-clearance padding (`pb-36 md:pb-12` / `pb-24 md:pb-12`) on the body container itself — where bottom padding exists at all, it is on the outer `min-h-screen` wrapper instead, which is a different (not necessarily wrong, but inconsistent) placement.

No `ALIGNED` status was assigned to any surface — none currently reproduce Studio's exact values.

### Deviation from instruction, with evidence

Section 5 of the implementation instructions specified `<StudioFeatureShell as="main">` for Verified Credits to preserve its `<main>` landmark. Live inspection (`document.querySelectorAll('main').length`) showed this produced **two** `<main>` elements on the page — the app-shell already renders one globally (`<main className="pb-36 lg:pb-0">`, confirmed present identically on Stage, which never had its own `<main>`). Two `<main>` landmarks on one document is an invalid nested-landmark violation, which the same instructions separately required checking for ("no invalid nested `<main>`"). Kept the `as` prop on the primitive itself (still available for a future page that genuinely lacks an app-level landmark) but did not use it here — `StudioFeatureShell` on Credits renders as a plain `div`, same as the other six surfaces. Verified the fix: exactly 1 `<main>` on the page afterward.

### Known follow-up, not blocking

Creative Circle and Match's content was authored for a narrower `max-w-2xl` well; widening to Studio's `max-w-6xl` is structurally correct (matches the canonical container) but leaves both surfaces' inner content visually looser than Studio's own dense grid layouts, since neither page's internal grid/spacing was redesigned for the wider well. This is a content-layout follow-up, not a container-alignment defect — flagging honestly rather than calling either surface fully finished cosmetically.
