## Answering the 14 required questions

**1. What does Kretopia need payments to do today?** Per the inventory: accept card payments for subscriptions and one-off purchases (tickets, invoices, payment links), hold and move money through a creator wallet, pay out creator earnings via Stripe Connect, take a platform fee on marketplace transactions, and verify creator identity for payout eligibility.

**2. Which features require regulated/provider infrastructure?** KYC/KYB (capability M), marketplace split payments and platform fees (N/O), payouts at scale (J), and card acceptance itself (A). These four are the capabilities where "just build it ourselves" is not a responsible option — they're the reason payment facilitators and licensed providers exist.

**3. Which flows can safely use bank transfer instructions?** Invoices (C) and payment links (D) that don't need marketplace split or card acceptance — these are exactly the two flows where Kretopia already has a partial, security-hardened precedent (`confirm_invoice_paid_manually`).

**4. Which flows must keep a provider for now?** Subscriptions (recurring billing + dunning), event/stage ticket checkout if it involves a platform fee, all creator payouts, and all KYC/onboarding.

**5. What does "free" actually mean in each flow?** For manual bank transfer: free means Kretopia charges no processing fee on that transaction — it says nothing about whether the payer's own bank charges *them* for sending a SEPA transfer, which depends on their bank and account plan. For SEPA Instant specifically: the EU's Instant Payment Regulation requires banks to price it at parity with standard SEPA Credit Transfer for their *customers* — this is a rule about what banks charge account holders, not a statement that any given payment API or provider is free to Kretopia. Every provider row in the table above that charges a percentage fee is a real cost to Kretopia regardless of what the end user's bank charges them.

**6. Which countries are in scope?** Not independently determined in this pass — the inventory found EUR/SEPA-country IBAN validation already built for DE/FR/NL/ES specifically, and separate routing-number support for US/CA/GB/AU. Any SEPA-focused migration is EUR/SEPA-zone-only by definition; it does not address the non-EUR countries already served.

**7. Which currencies are in scope?** Same answer as above — SEPA is EUR-only. This memo does not recommend any change for USD/GBP/CAD/AUD flows.

**8. What happens when a payment fails?** For the current Stripe paths: provider-driven error mapping exists (not independently re-verified in depth this pass beyond the checkout function). For a new manual-transfer flow: this needs explicit design — a failed/wrong-reference/underpaid transfer has no provider-driven failure signal at all, since there's no provider in the loop; Kretopia would need its own timeout/expiry and support-escalation policy.

**9. What proves a payment is received?** Today, for the two existing self-report RPCs: the word of the party being paid, plus a required free-text payment-method note — audited, but not independently verified. This is the single most important thing for you to decide deliberately for any new SEPA flow: keep this same trust model, or require something closer to real confirmation (a provider webhook, or a documented admin reconciliation process against a real bank statement).

**10. How is reconciliation handled?** See above — currently self-report only for the offline path; Stripe-webhook-driven for the online path. No generic admin reconciliation tool was found in this pass.

**11. How are refunds handled?** **Unresolved gap, confirmed in the inventory.** No generic refund edge function was found. This needs to be answered — by you or whoever owns the finance/support process today — before any migration plan can honestly claim refund parity with a new provider.

**12. How are payout balances protected?** Strongly, already: `wallet_credit`/`wallet_debit` are `service_role`-only with `REVOKE ALL` from every client role, confirmed by direct source read. This does not need to change for any migration option.

**13. What migration could be executed with the smallest risk?** Extending the existing `confirm_invoice_paid_manually` path with real SEPA bank-transfer instructions (beneficiary details, unique reference, amount, currency) displayed on the invoice payment page — in sandbox/test data only, no production invoice touched, no existing RPC authorization logic changed. This is Option 2 in the task's framing, scoped narrowly to invoices only (not payment links, not milestones, not subscriptions).

**14. What legal/compliance review is required?** At minimum, before any real (non-sandbox) SEPA collection flow goes live: (a) confirm whether displaying static bank-transfer instructions triggers any payment-services licensing obligation in Kretopia's operating jurisdiction(s) — in most read of standard practice this is treated as an "invoice with payment instructions," not a regulated payment service, but this needs actual counsel, not this memo's assumption; (b) confirm GDPR handling of any IBAN/bank-detail data now flowing through Kretopia's own database rather than a PCI/PSD2-licensed provider's vault; (c) if any Open Banking provider is later selected, confirm their own regulatory status (PISP license, passporting) covers Kretopia's operating countries.

## Recommendation

**Option 2, scoped narrowly, as a sandbox-only Phase 2** — extend the existing, already-security-hardened `confirm_invoice_paid_manually` path with real SEPA bank-transfer instructions for invoices specifically, while leaving every other flow (subscriptions, payment links, milestones, payouts, KYC) on Stripe exactly as it is today.

This is not Option 1 (do nothing) — real EU-invoice-collection value is added. It is not Option 4 (hybrid across multiple rails) or Option 6-style wholesale replacement — the marketplace-split and KYC capabilities that make wholesale replacement risky (rows N, O, M in the capability matrix) are untouched, because nothing about them changes. It draws on Option 3's philosophy (introduce the abstraction, migrate one low-risk flow first) but doesn't require a full provider-agnostic interface to be built before any value ships, since the RPC-based authorization boundary already exists and is already correct.

**Explicitly not recommended right now:** any Open Banking provider integration (Option 3 in the provider table) or marketplace-native platform migration (Option 6) — both are real, viable long-term options per the research above, but both carry `REQUIRES_COMMERCIAL_VERIFICATION` pricing and, for Option 6, `REQUIRES_LEGAL_REVIEW`-grade migration complexity (re-onboarding every creator's KYC). Neither should be decided from this memo alone.

**Before any code is written for even the narrow recommendation above**, I need your explicit approval on:
1. Whether to proceed with the sandbox-only manual SEPA invoice extension at all.
2. Whether to keep the existing "issuer self-attests" trust model for the new flow, or require something stronger (this is a real product/risk decision, not a technical one).
3. Whether the unresolved refund-handling gap (question 11) needs to be resolved first, given a payment flow without a clear refund path is a real support/trust risk regardless of rail.
